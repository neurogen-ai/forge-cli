# forge-cli — Release plan v0.6.0

Scope: PR lifecycle completion + CI visibility + triage. Everything an agent or maintainer needs to see what needs action, drive PR state to done, and keep triage moving. Builds on v0.4.0's write verbs and v0.5.0's discovery surface; `DoRaw` (v0.4.0) covers any text/plain needs.

Several endpoints here are version-dependent on the Forgejo instance (Actions runs, issue locking, notifications). Follow the house pattern: probe the live instance for each endpoint's presence before committing this checklist to implementation (see `scripts/probe-v0.3.0.sh` precedent).

## 1. Scope checklist

- [x] `forge pr checks N` — commit statuses plus Forgejo Actions runs for the PR head ref. Statuses always exist; Actions may not: print a loud `note: Actions not available on this instance` line instead of failing. (Implemented and unit-tested; the Actions-present path is pending live probe.)
- [x] `forge pr edit N [--title T] [--body B] [--add-reviewer U]... [--remove-reviewer U]...` — supersedes the v0.4.2 edit contract (title/body only, no clearing): this release adds reviewer request/removal and explicit field clearing. Backed by a `RequestedReviewers` extension in `internal/api/types.go` (subset rule still applies — add only what callers need). (Write endpoints pending live probe; read field and flags unit-tested.)
- [x] `comment edit ID [--body B]` / `comment delete ID` for both `pr` and `issue` spellings. Targets issue comments only; review-comment editing is out — the ID spaces differ (`pr comment resolve` already pins that precedent) and mixing them in one verb would make IDs mean different things per spelling. Record this decision in the help page.
- [x] `forge pr lock N [--reason R]` / `forge pr unlock N` — issue-backed conversation locking. (Lock endpoints pending live probe; error path surfaces the server message verbatim by construction.)
- [x] `forge status` — repo-scoped action dashboard: PRs assigned to me (via `requested_reviewers` / assignee filters), review requests awaiting my review, open issues. Scope decision on record: cross-repo mode is deferred until a repo-enumeration story exists; the v0.5.0 search contract is explicitly repo-scoped and `forge status` does not quietly break it. `CurrentUser()` from `internal/api/diagnose.go` resolves "me".
- [x] notifications: `forge notifications [--all]` (unread first) and `forge notifications read ID...` — server-side read state only, no local seen ledger (v0.3.0's remote-resolved-state rule). Picks up the thread deferred since v0.3.0 ("the unread loop is v0.4.0 territory") that never landed. (Batch mark-read with sequential fallback pending live probe.)
- [x] `forge label create NAME [--color C] [--desc D]` / `forge label edit NAME` / `forge label delete NAME` — triage lives in the daily loop and reuses v0.4.2's `resolveLabelIDs` + label table machinery, so this is nearly free.
- [x] `forge search issues|prs <query> [--state]` — moved here from v0.5.0 when that release re-scoped to the `gh`-compatible/`tuicr` backend contract; search is triage, not backend surface. Spec unchanged: `GET /repos/issues/search?q=...&type=issues|pulls&state=...`, table default on TTY (same spec shapes as `pr list` / `issue list`), JSON behind flag, pagination via the existing Link helper, result rows reusing existing table specs. (Search endpoint pending live probe.)
- [x] `forge pr sync-status [BRANCH]` — moved here from v0.5.0 for the same reason; a CI-visibility single-shot belongs beside `pr checks`. Spec unchanged: one request and exit (open PR for the branch, review state, CI), no daemon, no polling loop. Still the primitive v0.8.0's auto-sync service builds on. (Correction on record: the one request is a one-page open-PR list, not a by-branch GET.)

## 2. Notes

- Three distinct "statusy" commands after this release: `pr sync-status` (one branch, one PR, CI), `forge status` (one repo, everything needing action), `forge diagnose` (setup triage: host → token → owner → repo). README ships a paragraph distinguishing them.
- Reviewer removal (`--remove-reviewer`, `DELETE /pulls/{index}/requested_reviewers`) is the symmetric verb for `--add-reviewer`; both ship here. Assignee editing is not scheduled — say the word and it rides the same edit verb.
- Labels moved here from the release-engineering grouping: they are triage, not release ops, and reuse existing machinery.
- Dependency correction on record: `DoRaw` shipped in v0.4.0, not v0.5.0. The real gates for this release are endpoint presence (probe first) and the `RequestedReviewers` type extension.
- `search` and `sync-status` arrived from v0.5.0's re-scope (2026-08 goal change: v0.5.0 now owns the `gh`-compatible CLI surface and the `tuicr` `ForgeBackend` contract); see `plans/releases/v0.5.0.md` for the re-scope on record.

## 3. Parked

- Cross-repo `forge status` (needs a repo-enumeration product decision; the v0.5.0 search contract deliberately stays repo-scoped)
- Auto-merge (single explicit request is technically compatible with the one-shot contract, but it contradicts the no-auto-update philosophy — revisit only on demand)
- Webhook management (one-time configuration, not loop work)
- Issue assignee editing, pin/transfer/develop, review-comment editing
