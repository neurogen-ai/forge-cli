# forge-cli — Release plan v0.5.0

Scope: re-scoped around the new project goal — `forge` as a `gh`-style CLI for Forgejo with a stable machine interface, fit to serve as the Forgejo backend behind [`tuicr`](https://github.com/agavra/tuicr)'s `ForgeBackend` (tuicr shells out to `gh`/`glab`/`bkt` on other forges and owns no auth or forge API code; `forge` becomes its Forgejo equivalent, owning Forgejo interaction while tuicr keeps the review UX). This release lands the first tranche of that: the `gh`-compatible command surface, the anchored-comment capability tuicr cannot work without, and a contract audit that maps every `ForgeBackend` method to a `forge` command.

The previous "generic discovery" scope partly survives: `forge api` stays (it is an agent escape hatch and pure goal-aligned dogfood) and the `parseIndex` flag-placement change stays (options-anywhere ergonomics is exactly the `gh` muscle memory this release is about). `forge search` and `forge pr sync-status` moved to `plans/releases/v0.6.0.md` — neither serves the `tuicr` contract, and both fit that release's CI-visibility/triage themes. The implementation plan (`plans/implementation/v0.5.0.md`) still describes the old discovery-only split and needs re-cutting before implementation starts.

## 1. Scope checklist

- [x] `forge pr view N` — `gh`-spelling alias of `pr get`; both spellings work, `view` becomes the documented canonical form in README and help pages, `get` stays as a compatibility alias. Includes a `--json` field audit against what `tuicr`'s `get_pull_request`/`get_pull_request_info` actually read (title, body, author, head/base refs and SHAs, state, draft, timestamps, HTMLURL, mergeability where the instance exposes it).
- [x] `forge pr comment N --body T` — `gh`-spelling verb over the existing `comment add` machinery; without `--body` it is a usage error (no interactive editor; non-interactive is the contract). `--body -` reads the body from stdin for agents piping composed text. Missing body exits 2 before any request, matching `comment add`.
- [x] `forge pr review N --approve|--request-changes|--comment [--body T]` — `gh`-style flags over `review submit --state S`; both spellings accepted, flags become canonical. Same receipt and validation rules (`request-changes` requires `--body`, exit 2 before any request).
- [ ] anchored inline comments — **pending live-instance probe run** (no instance token in the J environment; `scripts/probe-v0.5.0.sh` committed but never executed — see §7 gap 1) — extend the comment surface with file/line/side anchoring (`--file P --line L [--side old|new]`, range if the instance supports it), so `tuicr` can post per-hunk comments. New endpoint territory; probe-first applies (see notes).
- [x] `forge pr checkout N` — fetch and check out the PR head locally (detached by default, `--branch B` to name a local branch). Pure local git after the metadata fetch; no Forgejo mutation. Not required by `tuicr` today, but it is in the `gh` target vocabulary and cheap next to the rest.
- [x] `forge api <path> [--method M] [--input @file|JSON] [--jq Q]` — unchanged from the discovery scope; kept because agents scripting around CLI omissions is core to the new goal, and internal dogfooding (`forge api repos/{o}/{r}/swagger.v1.json`-style probes) is how this release's endpoint work gets done.
- [x] cli: numeric-token-tolerant flag placement — `parseIndex` accepts the first numeric arg wherever it appears (`forge pr merge 11 --merge` and `forge pr merge --merge 11` both work). Flag-aware scan (not naive first-numeric) so numeric flag values (`pr conv --min-unresolved 2 11`, `pr merge --subject 42 11`) are not mis-grabbed. Applies to every N-taking command (~10).
- [x] tuicr `ForgeBackend` contract audit — derive the method list from tuicr's current `ForgeBackend` trait (not from guesswork), map each method to the `forge` command that serves it, and record gaps in this document. `list_pull_requests` → `pr list`, `get_pull_request`/`get_pull_request_info` → `pr view`, `get_pull_request_diff` → `pr diff` are expected to pass on arrival; comments, reviews, and submission depend on the items above.
- [x] README: the `gh` → `forge` mapping table, the explicit "`forge` is a `gh`-style CLI for Forgejo" statement, the documented exit-code contract (0 success / 1 runtime-API / 2 usage / 3 repo-context / 4 auth / 5 network — already implemented in `internal/cli/exit.go`, this item is documentation not code), and the JSON-output contract (JSON on stdout, diagnostics on stderr, receipts always JSON). Plus a short agent-skill paragraph showing the six-command workflow (`pr list / view / diff / comment / review / merge`) so a skill can be written against `forge` with no Forgejo knowledge.
- [ ] end-to-end lifecycle test against a real Forgejo instance: **pending a real-instance run** (no reachable instance with a token in the closing environment; see §7). open PR → `pr view` → `pr diff` → `pr comment` → anchored inline comment → `pr review --approve` / `--request-changes` → `pr merge`. This is the release's acceptance criterion, and the demonstration that a `tuicr` Forgejo backend can run the complete review lifecycle through `forge`.
- [x] release commit sequence: first commit bumps `forge.Version` (the central constant landing in v0.4.2) to `v0.5.0` so the binary, tag, and this document agree.

## 2. Notes

- What already exists and is *not* in this checklist (the audit verifies rather than builds): `pr list`, `pr diff` (raw `.diff`/`.patch` bytes, exactly what `get_pull_request_diff` wants), `pr close/reopen/ready`, `pr merge --merge|--squash|--rebase` with `--subject/--body/--delete` and branch deletion only after confirmed merge, `pr comment add` / `review submit --state` receipts, the full non-interactive auth chain (`--token` > config > `FORGE_TOKEN` > git credential fill, GCM optional), repo-context resolution (flag > env > local config > global config > git remote), TTY-aware JSON/table output, and exit codes 0–5. Most of the goal's Definition of Done is already green; this release closes the named-command gaps and proves the rest end to end.
- Alias policy: old spellings (`pr get`, `pr comment add`, `review submit --state S`) stay and keep their current receipts. The `gh` spellings become canonical in docs and help; each help page shows both. Migration path is old interface → compatible aliases → `gh`-compatible canonical, so nothing breaks for existing users (house rule: receipts and flags that exist today do not change shape mid-release).
- Anchored comments are the one genuinely new transport surface. Forgejo's anchoring API differs from GitHub's (positions land on the issue-comment/review-comment endpoints with line and side fields, and the accepted shape varies by Forgejo version), so: probe the target instance first (`scripts/probe-v0.3.0.sh` precedent), then commit the flag set. If the instance cannot anchor a comment, the command must fail with the standard error path (exit 1, server message in the hint) — a predictable failure, never a silently unanchored comment.
- `pr checkout`: resolve the PR head (including cross-repo heads, where `pr view` already carries source repo), fetch into the local repo, check out the head SHA detached by default. Local-branch naming via `--branch`; no writes to Forgejo. Failure modes mirror `pr pull`'s repo-context rules.
- `forge api <path>` detail (unchanged from the discovery notes): path joined onto baseURL (leading slash optional), repeatable `--q k=v` for query params (no shell quoting games), body via `--input -` (stdin) or inline JSON, `--method` defaults GET; decode-as-JSON when content-type is JSON, raw passthrough otherwise. Document the auth-header caveat (the token goes anywhere the agent sends it).
- Flag placement: "options anywhere" wins over POSIX "options first" because this CLI follows subcommand grammar (git/docker style), not `grep`-style utility syntax. Moved here from v0.4.2 originally: `parseIndex` is shared by every N-taking command, and the change touches flag parsing plus test expectations across the suite — not micro-patch material.
- `pr merge --dry-run` is deliberately **not** in scope: Forgejo cannot simulate a merge over the API, so a dry run could only repeat the local containment check (`create-batch` preflight), which says nothing about server-side conflicts and would promise a safety it does not have. Mutations stay explicit one-shot commands; `create-batch` keeps the plan/dry-run pattern where it is real.
- Unsupported-operation behaviour: if the ForgeBackend audit hits a GitHub capability Forgejo does not have, the answer is the existing error path (typed exit code, server message on stderr), not a pretend success. No new error machinery planned; revisit only if the audit finds agents need a machine-readable `unsupported_operation` marker, and record that finding here if so.

## 3. Defer

- `forge search` and `forge pr sync-status`: moved to `plans/releases/v0.6.0.md` (CI-visibility/triage fit; neither is on the `tuicr` critical path).
- Review-thread editing/deletion, `pr comment view` as a separate gh-spelling listing verb (`pr conv` already covers thread retrieval for `tuicr`), and any `--json <fields>` field-selection syntax beyond the existing `--json` flag.
- Multi-forge ambitions, review UI, session state, diff rendering — permanently out of scope per the goal statement; `forge` is the transport layer, `tuicr` owns the review experience.

## 4. Done when

- Every `tuicr` `ForgeBackend` method resolves to a documented `forge` command, with gaps (if any) listed in this document.
- The six-command `gh` workflow (`pr list / view / diff / comment / review / merge`) works on a real Forgejo instance from a fresh clone with only `FORGE_TOKEN` set, with no prompts and no Forgejo-specific knowledge.
- A developer who knows `gh` can run `forge pr view 123`, `forge pr review 123 --approve`, and `forge pr merge 123 --squash` without reading the manual; existing `forge` users' scripts keep working unchanged.

## 6. ForgeBackend contract audit

Derived from tuicr's `ForgeBackend` trait at commit `81bfe6d7961a4cb64c7dbe22317b30719e833594`
(2026-09-09, `src/forge/traits.rs`). Required methods are those without a default body;
defaulted methods are listed with the behaviour the default supplies.

| Trait method | Kind | forge command | Status |
|---|---|---|---|
| `list_pull_requests` | required | `pr list` | served |
| `get_pull_request` | required | `pr view` | served |
| `get_pull_request_info` | default: builds from `get_pull_request` | `pr view` | served by default |
| `get_pull_request_diff` | required | `pr diff` | served (raw `.diff`/`.patch` bytes, exactly what the trait's `FilePatch` pipeline parses — the same endpoint tuicr's own `tea` Gitea backend calls directly) |
| `fetch_file_lines` | required | — | **gap**: no forge command fetches file contents at a revision. Reachable through `forge api` against the repo contents endpoint, but not as a typed command |
| `file_line_count` | default: `Ok(0)` | — | served by default; a real count is reachable through `forge api`, same as `fetch_file_lines` |
| `list_review_threads` | required | `pr conv` | served (thread retrieval with resolution state) |
| `list_review_summaries` | default: empty | — | served by default (GitHub-only review-summary semantics) |
| `list_pull_request_commits` | required | — | **gap**: no forge command lists a PR's commits |
| `list_pull_request_review_metadata` | default: empty | — | served by default |
| `get_pull_request_commit_range_diff` | required | — | **gap**: no cumulative sub-range diff command; `pr diff` covers the PR head-to-base diff only |
| `local_checkout_path` | default: `None` | `pr checkout` | served by default (optimization hook); `pr checkout` puts a local checkout in reach, but forge does not report a path to the caller |
| `create_review` | required | `pr review --approve\|--request-changes\|--comment` + `pr comment --file/--line/--side` | served for the event, body, and inline comments; `commit_id` has no forge equivalent (Forgejo review comments anchor to diff positions, not commit SHAs) — recorded as a finding, not invented |

Findings:

- The three required-method gaps (`fetch_file_lines`, `list_pull_request_commits`,
  `get_pull_request_commit_range_diff`) all have a possible escape-hatch route through
  `forge api`, but no typed command. None needs a machine-readable `unsupported_operation`
  marker: each is a missing convenience query, not an unsupported mutation, and the
  existing typed error path (exit 1, server message on stderr) covers any request tuicr
  sends that forge cannot answer. Revisit if tuicr's Forgejo backend needs these
  first-class rather than through `forge api`.
- `create_review.commit_id` maps to nothing in Forgejo's review-comment transport. tuicr
  callers passing a commit id should expect forge to ignore it; if that matters for
  correctness, it belongs in the same follow-up conversation as the gaps above.

## 7. Acceptance record

Recorded at the v0.5.0-contract-close head. All boxes in §1 are ticked only
where their acceptance run exists; boxes 4 and 10 stay unticked because no
Forgejo instance with a token was reachable in the closing environment.

Binary battery (all green on the closing head):

- `go vet ./...` clean, `gofmt -l .` prints nothing, `go build ./...` and
  `go test ./...` pass across all packages.
- `forge version` prints `forge-cli v0.5.0` (`version.go` constant and
  `cmd/forge/main.go` print line agree).
- Every new help page exits 0: `pr view -h`, `pr comment -h`,
  `pr review -h`, `pr checkout -h`, `forge api -h`.

Flag placement: the index-placement test battery passes (nine `--- PASS`
rows in `internal/cmds/index_placement_test.go`, plus per-command placement
tests from Branch A). Live binary check of both argument orders
(`pr merge 11 --merge` / `pr merge --merge 11`) parsed the index correctly
and proceeded to auth, which fails in this environment; the battery is the
evidence for the placement cases.

Gaps, stated plainly:

1. **Probe not run.** `scripts/probe-v0.5.0.sh` (F1) was never executed: no
   instance token exists in the closing environment. The anchored-comment
   wire encoding shipped as the documented contract skeleton in
   `internal/api/pulls.go` (`AnchorToWire`), not a probe-confirmed shape.
   The known sharp edge: when the server accepts the POST but the response
   omits the `comments` array, the command rebuilds the receipt from user
   input and prints success, so a server that silently ignores anchor
   fields would yield a success receipt for an unanchored comment. A 422
   rejection stays the standard exit-1 path with the server message. This
   is the top item for independent instance testing; the probe script
   decides the real encoding in one run.
2. **`--q` same-key collapse.** Repeatable `--q k=v` in `forge api`
   preserves order in `flagValues`, but the transport's `url.Values.Set`
   collapses two `--q` flags with the same key to the last value. No in-scope
   endpoint needs duplicate keys.
3. **`reviewEvent` error text names `pr review submit`.** Validation errors
   under the gh flags form (`pr review --request-changes` without `--body`)
   print the submit spelling in the message prefix, because both spellings
   share one validation path. Exit code and behaviour are identical.
4. **Auth resolves before usage validation.** With no token available, a
   missing `--body` surfaces as exit 4 (auth) rather than 2 (usage),
   because the framework runs `RequiresAPI` token resolution before the
   command body validates. Identical on v0.4.2 (`pr comment add 5` exits 4
   there too), so it is pre-existing framework behaviour, not a v0.5.0
   regression. No request is made in either case, and with a resolvable
   token the missing-body path exits 2 as contracted.

The §1 boxes left unticked are exactly the two the rule reserves:
anchored inline comments (box 4, probe never run) and the end-to-end
lifecycle (box 10, no real-instance run). An unreachable instance stops J
and reports; these stay open until that run happens.
