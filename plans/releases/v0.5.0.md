# forge-cli — Release plan v0.5.0

Scope: generic discovery. The raw response transport landed in v0.4.0 (`Client.DoRaw`); this release builds the passthrough, search, and status commands on top of it. Implementation detail gets its own plan when this release is scheduled.

## 1. Scope checklist

- [ ] `forge api <path> [--method M] [--input @file|JSON] [--jq Q]`
- [ ] `forge search issues|prs <query> [--state]`
- [ ] `forge pr sync-status [BRANCH]`

## 2. Notes

- `forge api <path>` sends the configured host/token directly: path joined onto baseURL (leading slash optional), query params via repeatable `--q k=v` (no shell quoting games), body via `--input -` (stdin) or inline JSON. Response: decode-as-JSON if content-type is JSON else raw text passthrough to stdout. `--method` defaults GET. This exists for agents scripting around CLI omissions (the same gaps we kept hitting during design); document the auth-header caveat (token goes anywhere the agent sends).
- Useful internal dogfood: `forge api repos/{owner}/{repo}/swagger.v1.json`-style probes replace ad-hoc curl during feature work.
- `forge search issues|prs <query>` covers both lists through `GET /repos/issues/search?q=...&type=issues|pulls&state=...`. Table default on TTY (same spec shapes as `pr list` / `issue list`), JSON behind flag, pagination via the existing Link helper. Result rows reuse existing table specs.
- `forge pr sync-status [BRANCH]` is a single-shot status check (open PR for the branch, review state, CI) that Starship or another prompt invokes repeatedly. The command runs one request and exits; it is not a daemon and starts no polling loop. Long-running sync behaviour is v0.6.0's problem, not this one.
