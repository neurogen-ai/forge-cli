# forge-cli — Release plan v0.1.2

Theme: name the culprit when `pr create` 404s instead of echoing the server's raw "The target couldn't be found."

## Problem

`forge pr create --title test --base main` on a Forgejo repo returns:

```
error: 404: The target couldn't be found.
```

(see Neurogenesis/forge-cli issue #2). The wiring preflight cannot catch this:
host, token, owner, and repo all verified fine before the command ran, so the
POST itself is what fails. On Gitea/Forgejo that POST 404s for three distinct
reasons and today nothing says which:

1. the base branch does not exist
2. the head branch does not exist
3. pull requests are disabled for the repo (or it is a mirror)

Gitea still serves branch endpoints when pulls are disabled, which makes the
three-way split decidable by probing.

## Behaviour

On `*APIError` with status 404 from `CreatePullRequest` only:

- Probe base branch (`GET /repos/{o}/{r}/branches?branch={base}`), then head.
- base missing → exit 3, msg `base branch "<base>" not found in <owner>/<repo>`,
  hint names `--base / FORGE_BASE / [defaults] base` and quotes the server's
  original message.
- else head missing → same shape for head, hint names
  `--head / FORGE_HEAD / current git branch`.
- else → exit 3, msg `repository <owner>/<repo> does not accept pull requests`,
  hint: branches were verified but the POST still 404'd; enable PRs in repo
  Settings or check `--repo`; quote the server message.
- Probe errors (transport/auth) fall through to the third case rather than
  masking the original 404; verbose request lines already flow through the
  client logger, so nothing extra is logged.
- Every other status keeps today's exact `mapErr` output.

No extra requests are made on successful creates.

## Implementation notes

- New probe follows the existing pattern in `internal/api/repo.go`
  (`OwnerExists`/`RepoExists`): 404 → false + nil error, anything else is an
  error so a scope problem is never mistaken for a missing branch.
- Disambiguation lives in `internal/cmds/pr.go`, not in `mapErr`: the generic
  error funnel has no owner/repo/branch context, and bolting pr semantics onto
  it invites every other command to add special cases.
- Post-hoc probing beats pre-probing: zero cost on the happy path, no race
  window wider than milliseconds, correct message either way.
- Server message quoted always, not behind `-v`: it is one line, it is what
  users paste into bug reports, and diagnose hints already quote server text.

## Tests

httptest against a real `*api.Client`, matching existing convention
(`internal/cmds/pr_test.go`):

- `internal/api/branch_test.go`: branch 200 → true+nil; 404 → false+nil;
  403 → error.
- create returns 404 + both branch endpoints 200 → ExitContext,
  "does not accept pull requests".
- create 404 + base endpoint 404 → "base branch" message.
- create 404 + head endpoint 404, base OK → "head branch" message.
- create 500 → unchanged mapErr output.

## Acceptance criteria

1. `forge pr create --base nonexistent` on a real repo exits 3 naming the base
   branch, quoting the server message in the hint.
2. Same for a bad head.
3. On a repo with PRs disabled, create exits 3 saying so.
4. Successful creates make no extra requests beyond the POST.
5. `go test ./...` green.
