# forge-cli — Release plan v0.4.1

Scope: batch correctness. v0.3.1's `create-batch` opened PRs in lexical branch order and never re-checked base containment, so merging any superset branch (or any branch before its stack parent) left the remaining PRs with 0 code changes: the branch tip was already an ancestor of the updated base. This release makes the batch order merge-safe, detects empty diffs before they become PRs, waits for the server to finish processing each POST, and treats duplicate-PR responses as skips instead of failures. All PRs still target the same resolved base (default chain or `--base`); no stacked-PR base inference.

The thin HTTP verbs that previously lived here moved to `plans/releases/v0.4.2.md`.

## 1. Scope checklist

- [ ] gitctx: `BranchTipDate` helper returning the branch tip's committer date (`%(committerdate:unix)`), matching what lazygit shows; lazygit is the fidelity bar; with tests
- [ ] gitctx: `IsAncestor` helper (`git merge-base --is-ancestor`), error contract matching existing helpers; with tests
- [ ] `create-batch`: plan ordered by tip date ascending; ties broken by `IsAncestor` (parent branch first), then lexically
- [ ] `create-batch`: preflight skips branches whose tip is already contained in the resolved base, reported on stderr as `skipped: <branch> (already in base)`; all-skipped keeps exiting 2 and the empty-plan error message must cover the containment case (e.g. "all matching branches already contained in base"), not just the no-subject case
- [ ] `create-batch --yes`: after each POST, poll until the PR page is available before posting the next; bounded retries, warn-on-timeout on stderr, never fails the batch
- [ ] `create-batch --yes`: a `PR already exists for that branch -> <base>` server response is a skip, not a failure: stderr note in the existing `skipped: <branch> (<reason>)` style and continue with the remaining branches
- [ ] README + tick this checklist; acceptance battery (`go vet ./...`, `gofmt -l .` empty, `go build ./...`, `go test ./...`) with acceptance notes in the v0.3.1 style

## 2. Notes

- Root cause on record: v0.3.1 stacked branches all target one base; lexical sort order put superset branches before their parents (api contained gitctx commits, batch contained nearly everything). Merging in PR-number order then emptied the still-open parent PRs. Not a client race — the `--yes` loop was already strictly sequential — and not an age-calculation bug; the server's diffs were correct.
- Ordering: committer date is the only branch age git records (reflogs are prunable), so it is the honest ceiling and matches lazygit. Equal dates (rebase, amend, same-second scripted commits) fall through to ancestry, then lexical.
- Containment check runs locally against the resolved base before any POST: `UniqueCommitCount(base, branch) == 0` and the `IsAncestor` helper together make a locally-empty PR impossible to open, no server round-trip needed.
- Page-available poll: GET the PR's `HTMLURL` directly (plain HTTP, no JSON decode, no auth) until status < 400. Bounded (about 5 attempts, ~500ms apart). Timeout is not an error: the PR exists; print `note: <branch> page not confirmed available before continuing` on stderr and keep going. On private repos the unauthenticated poll may time out every time; that is accepted noise. The POST loop stays strictly sequential with stop-on-first-failure unchanged.
- Duplicate-PR detection: best-effort substring match on the server's message (`serverMessage` of the APIError). The exact text is unverified against the live instance; treat both the matcher and the wording as provisional until confirmed, and record the server message verbatim in the receipt item's `Error` field so stdout still shows why no PR landed. Stop-on-first-failure applies to every other failure class.
- Receipt contract unchanged: same `BatchReceiptItem` type for plan and receipt; skipped branches never appear as receipt items in dry-run, and only carry `Error` in `--yes` receipts.

## 3. Defer

- Stacked-PR base inference (each batch PR targeting its parent branch): eliminates growing diffs entirely but needs design around merge-deleted base branches and Forgejo's handling of PRs whose base vanished. Candidate for a 0.5 proposal.
- Duplicate detection without posting (dry-run preflight via the PR search endpoint): only worth it if the POST-time matcher proves unreliable.
