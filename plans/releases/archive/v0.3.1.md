# forge-cli — Release plan v0.3.1

Scope: a small follow-up to v0.3.0 focused on PR creation ergonomics. `pr conv` becomes the PR landing view, `pr create` stops demanding flags it can infer, and stacked branches get a safe batched-open verb. Everything else (write verbs, api passthrough, search) stays in v0.4.0.

Decisions below follow recon + oracle review; the raw feature list this plan replaces is preserved in git history (`plans/releases/v0.3.1.md` pre-rewrite).

## 1. Scope checklist

- [x] `forge pr` / `forge pr -h` print the `conv` help page as the landing text, extended with a compact "other PR commands" index (`create`, `list`, `get`, `review`, `resolve`)
- [x] `pr create` auto-title: omitting `--title` derives it from the branch tip's commit subject (`git log -1 --format=%s`)
- [x] `pr create` auto-base: after existing fallbacks, resolve git's default branch (`origin/HEAD` → server `default_branch`); never hardcode `main`
- [x] `forge pr create-batch PATTERN [--base B] [--yes]`: open PRs for matching local branches, dry-run by default
- [x] gitctx helpers: commit subject, base resolution, `<base>..HEAD` commit check, local-branch glob listing
- [x] API: fetch repository `default_branch` (new method; there is only `RepoExists` today)

Out of scope: branch ordering / creation-dependency tooling (deferred to v0.4.x or a proposal), stacked-PR base inference, automatic push, duplicate-PR reconciliation, batch rollback, title templates.

## 2. PR landing page

The registry auto-generates `forge pr` help from member summaries (internal/cli/help.go). That generation is bypassed for the `pr` family: bare `forge pr` and `forge pr -h` print `prConvCmd.HelpPage()` verbatim, appended with a one-line-per-command index of the other PR verbs. Direct `forge pr <sub> -h` is unchanged. Rationale: conv is the day-to-day surface; the generic member dump buries it.

## 3. `pr create` defaults

New precedence, per flag:

- `--title` (exit 2 if missing/empty today) → unchanged when given; when omitted, derive from the current branch tip's commit subject. Empty subject (or `<base>..HEAD` empty — no unique commits) → exit 2 with a hint naming `--title` or branch content, rather than opening a misleading PR.
- `--base` → `$FORGE_BASE` → `[defaults].base` (config) → `git symbolic-ref --short refs/remotes/origin/HEAD` → server `GET /repos/{o}/{r}` `default_branch` → exit 2 with a `--base` hint. No `git remote set-head` mutation, no hardcoded `main`/`master`.
- `--head` precedence unchanged.

## 4. `pr create-batch`

```
forge pr create-batch PATTERN [--base B] [--yes]
```

- `PATTERN` is a git glob over local branch names (`git for-each-ref`); no matches exits 2.
- All PRs target the same resolved base (§3 logic). No stacked/dependency inference in this release — the branch-ordering research item feeds a future design.
- Titles from each branch tip's commit subject (§3 rules). Preflight rejects zero-commit or empty-subject branches before any POST.
- Dry-run by default: prints the planned creates (branch → title/base), exits 0, mutates nothing. `--yes` performs the POSTs.
- Output: always-JSON receipt array in the `PullReceipt` style (writeJSON, ignoring `--json`/`--table`), one entry per branch (`branch`, `title`, `base`, `url`/`error`).
- Failure semantics: stop on the first failed POST, report server message verbatim through the APIError contract, preserve prior successes in the receipt, never retry or roll back. Batch creation is not transactional; partial success is expected and visible.

## 5. Package layout

```
internal/cli/help.go          # pr-family help override (conv landing page)
internal/cmds/pr.go           # title/base inference in prCreateCmd; create-batch cmd
internal/cmds/pr_batch.go     # batch preflight + receipts
internal/gitctx/repo.go       # commit subject, base resolve, ancestry check, branch glob
internal/api/repo.go          # repository fetch → default_branch
```

## 6. Build order

1. Help routing: conv landing page + index, tests for `forge pr`, `forge pr -h`, direct subcommand help
2. gitctx helpers (subject, base resolve, ancestry, branch glob) with detached-HEAD / unborn-branch / missing-base tests
3. API `default_branch` method; refactor `pr create` to the new precedence
4. `pr create-batch`: preflight, ordering, dry-run default, `--yes`, receipts, partial-failure tests
5. README + this checklist; full `go vet ./...`, `gofmt -l .`, `go build ./...`, `go test ./...`

## 7. Residual risks

- `origin/HEAD` can be stale or absent; the server `default_branch` fallback is authoritative.
- Local branches may be unpushed; batch POSTs fail per-branch and surface the server message verbatim.
- Batch creation can partially succeed (no transaction); the receipt is the source of truth for what landed.

## 8. Acceptance notes (v0.3.1)

`go vet ./...` (clean), `gofmt -l .` (empty output), `go build ./...`,
`go build -o /tmp/forge ./cmd/forge`, and `go test ./...` (all nine packages
`ok`; `internal/cmds` the slowest at ~0.7s).

- `forge pr | head -5` prints the conv help page verbatim as the landing
  surface (`use: forge pr conv N [--all] [--min-unresolved N]` first line),
  with the "Other pr commands:" index following; exit 0. Confirms conv-first
  landing is wired through `SetGroupPage("pr", ...)` in `cmd/forge/main.go`.
- `forge pr create-batch 'v0*'` (dry-run by default, nothing posted) prints the
  JSON plan for all seven `v0.3.1-*` branches — branch, auto-title from each
  branch tip's commit subject, base resolved to `main` — and exits 0 without
  posting or touching the network.
- `forge pr create-batch 'zzz-no-match*'` (pattern matching no local branch)
  exits 2 with `error: no branches match "zzz-no-match*"` plus the usage hint
  and help page, as specified in §4.
