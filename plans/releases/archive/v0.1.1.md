# forge-cli — Release plan v0.1.1

Theme: friendly handling of "empty" collection endpoints that 404 instead of returning an empty array.

## Problem

Gitea/Forgejo return `404: The target couldn't be found.` from collection
endpoints when the feature has never been used on a repository — e.g.
`GET /repos/{o}/{r}/pulls` on a repo with no PRs yet (the PR unit/path is
not initialised). Today this escapes `mapErr` as the raw server text:

```
error: 404: The target couldn't be found.
```

This is misleading: the wiring preflight (`cmd/forge/diagnose.go`) already
verified host, token, owner, and repo seconds earlier, so the user is left
thinking something is missing when the real answer is simply "there are
none yet".

## Behaviour

For **list** commands only (`pr list`, `issue list`; anything later that
returns a collection):

- A 404 from the collection endpoint is interpreted as an empty result.
- stdout still emits valid JSON for scriptability: `[]`.
- stderr prints a human note: `no <item being listed> found`
  (e.g. `no pull requests found in <owner>/<repo>`), exit code 0.
- With `--verbose`, print the full original server response (status +
  message) to stderr before the friendly note, so genuine misconfiguration
  can still be spotted.

Non-list commands (`pr get N`, `pr conversation N`, `issue get N`) keep the
current behaviour: a 404 on a single item is a real error and must surface
as-is.

## Implementation notes

- Do this in the api layer or at the call site, not by weakening
  `mapErr` globally: add a helper (e.g. `api.NotFoundAsEmpty(err) bool`)
  or have `ListPullRequests`/list helpers return `nil, nil` on 404 so
  callers can't forget it. Prefer the api-layer approach so every future
  list endpoint inherits it.
- The wiring preflight is unaffected: it probes `/repos/{o}/{r}` directly,
  which does NOT 404 on an unused PR unit, so diagnosis stays exact.
- Keep the disambiguation rule from v0.1 intact: a 404 there still means
  wrong name / private repo / missing scope — never an empty list.

## Tests

- httptest: `/repos/{o}/{r}/pulls` returns 404 with Gitea-style body
  `{"message":"The target couldn't be found."}` → list command exits 0,
  stdout is `[]`, stderr contains `no pull requests found`.
- Same server with `--verbose`: stderr also contains the raw status/message.
- Single-item 404 (`pr get 99`) still maps to a typed error (exit 3).

## Acceptance criteria

1. On a fresh repo with zero PRs: `forge pr list` → exit 0, stdout `[]`,
   stderr `no pull requests found in <owner>/<repo>`.
2. `forge pr list -v` additionally shows the full server message.
3. `forge pr get <missing>` still fails loudly.
4. `go test ./...` green.
