# forge-cli — Release plan v0.4.0

Scope: complete the conversation loop with write verbs and add generic discovery. Every verb here is thin HTTP over endpoints we already know exist; no local state, receipts follow the pull pattern where anything mutates.

Carried notes from earlier drafts (still in scope):
- starship CLI view (appears in projects with the config dir present) that polls the configured server at an interval and reports when local is out of sync

## 1. Scope checklist

- [ ] `forge pr review submit N --state approve|request-changes|comment [--body T]`
- [ ] `forge pr comment add N --body T` / `forge issue comment add N --body T`
- [ ] `forge pr close N` / `forge pr reopen N` / `forge pr ready N`
- [ ] `forge pr diff N` (Forgejo `.diff` suffix URL) + `--patch`, `--out` writing into `.forge/cache/`
- [ ] `forge pr merge N --merge|--squash|--rebase [--delete] [--subject S] [--body T]`
- [ ] `forge api <path> [--method M] [--input @file|JSON] [--jq Q]`
- [ ] `forge search issues|prs <query> [--state]`

## 2. Verbs

### review submit

POST `/repos/{o}/{r}/pulls/{index}/reviews` with body `{event, body}`. `--body` required for `request-changes`; validation error exits 2 otherwise. Output: JSON receipt of the created review (id, state). Reuses `Review` struct extended in 0.3.0.

### comment add

POST `/repos/{o}/{r}/issues/{index}/comments` works for both PRs and issues in Forgejo (PRs are issues underneath); both spellings route to one client method. JSON receipt back (id, HTMLURL).

### close / reopen / ready

- PRs: PATCH `/repos/{o}/{r}/pulls/{index}` `{"state": "closed"|"open"}`.
- `pr ready N`: PATCH `/pulls/{index}` `{"draft": false}`; server versions lacking draft support surface the message verbatim, exit 1.
- Issues already have close/open from 0.3.0 stage 5.

### diff

GET `/repos/{o}/{r}/pulls/{index}.diff` (and `.patch`). Text/plain response; default prints to stdout (it IS a view verb — pure), `--out` writes `<repo>-<N>.diff` into `.forge/cache/prs/` reusing the overwrite store function from pull. Receipt style printed when written.

Careful: this endpoint bypasses the JSON client (`Client.Do` decodes JSON); needs a raw-text method on the API client.

### merge

POST `/repos/{o}/{r}/pulls/{index}/merge` with `Do` field values matching gh semantics: `merge|squash|rebase`. Flags map directly; `--delete` then DELETEs `/repos/{o}/{r}/git/refs/heads/<head>` after successful merge. Conflict/WIP/unprotected failures come back as non-2xx: print server message verbatim, exit 1, never retry automatically. Merge requires up-to-date base handling per Forgejo defaults; do not invent auto-update behaviour (documented anti-goal pending `update-branch` demand).

### api passthrough

`forge api <path>` sends the configured host/token directly: path joined onto baseURL (leading slash optional), query params via repeatable `--q k=v` (no shell quoting games), body via `--input -` (stdin) or inline JSON. Response: decode-as-JSON if content-type is JSON else raw text passthrough to stdout. `--method` defaults GET. This exists for agents scripting around CLI omissions (the same gaps we kept hitting during design); document the auth-header caveat (token goes anywhere the agent sends).

Useful internal dogfood: `forge api repos/{owner}/{repo}/swagger.v1.json`-style probes replace ad-hoc curl during feature work.

### search

`GET /repos/issues/search?q=...&type=issues|pulls&state=...` covers both lists in Forgejo/Gitea. Table default on TTY (same spec shapes as pr list / issue list), JSON behind flag, pagination via existing Link helper. Results rows reuse existing table specs.

## 3. Conventions carried from 0.3.0

- View/pull split unchanged: `api` and `search` and all read paths stay pure; mutating verbs emit JSON receipts; conflicting global `--json/--table|-t` still exit 2.
- No prompts, no confirmations: destructive-ish verbs (merge, close, delete ref) are explicit single-shot; dry-run not needed because blast radius is one object unlike resolve-all.
- Exit codes unchanged; server messages verbatim through APIError.

## 4. Build order

1. PR state verbs + review submit + comment add (all JSON-client methods)
2. diff raw-text client method
3. merge + ref deletion
4. api passthrough
5. search
