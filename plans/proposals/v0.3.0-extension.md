# forge-cli v0.3.0-extension: what gh does that we still don't

Source basis: gh CLI's public command surface (training knowledge of v2.x; not verified live this session). Filtered through the philosophy we converged to in v0.3.0: agent-driven JSON stdout, remote state as truth, view verbs pure / pull writes, unresolved as the working filter, loud failures, zero third-party deps. Those defaults are ours to stray from where gh's ergonomics win outright; the deviations are marked.

Grouped by how well each fits. "Fit" means: serves the agent/dev conversation loop over the Forgejo API without dragging in daemon/state machinery we just deleted.

## Tier 1: complete the existing loop (strongest fits)

| gh command | forge proposal | Why it belongs next |
|---|---|---|
| `pr review` | `forge pr review submit N --state approve\|request-changes\|comment [--body T]` | Closes the other half of the fix-and-respond loop. We resolve reviewer threads; this lets maintainers-turned-reviewers send new reviews. Pure POST. |
| `pr comment`, `issue comment` | `forge pr comment add N [--body T]`, same for issues | Replying is the natural action after reading a thread; currently impossible except by resolving. |
| `pr close`, `pr reopen`, `draft toggle` (`ready`) | same names | Whole-object state changes mirror the accepted issue close/open pattern. PATCH. |
| `pr diff` | `forge pr diff N` | Forgejo serves `.diff` and `.patch` directly off `/pulls/{index}.diff`. One GET, trivially cacheable into `.forge/cache/`. Original v0.3.0 release-note territory ("track diffs") finally satisfied natively. |
| `pr merge` | `forge pr merge N [--merge\|--squash\|--rebase] [--delete] [--subject] [--body]` | The loop ends here. Needs careful error surfacing (conflicts, WIP protection); server messages verbatim per contract. |
| `api` passthrough | `forge api <path> [--method M --input J]` | Explicitly valuable *because* we keep finding API gaps (resolve endpoint versions, timeline fields). Lets agents script around our omissions instead of waiting on us. Precedent: gh treats `gh api` as first-class. |
| `search` | `forge search prs/issues [q]` backed by list endpoints' `q` params | Agents need discovery ("find me the PR for X"). Server-side query beats local grep of dumps. |

## Tier 2: useful, modest effort, do after 0.3.0 stabilises

- `forge pr edit N --title/--body`; `forge issue edit`
- `forge label list/add/remove N` on issues and PRs (id resolution machinery exists already from issue create)
- `forge pr checks N` / `forge run list|view|watch` against Forgejo Actions (Forgejo exposes runs; polling receipts fit the receipt pattern from pull). Note Forgejo Actions API coverage lags GitHub's; needs the live-instance probe treatment like resolve.
- `forge repo view N/edit` (description, website, default branch)
- `forge release list/get/create/download` — repo-scoped, no local state needed, agents fetching release assets is common
- `forge pr update-branch` style helper (merge base back in) if resolve-everything loops show stale branches mattering
- `browse`: open current item in browser (`forge pr browse N` prints or opens HTMLURL we already carry)

## Tier 3: probably never, documented as anti-goals

- `gist`, `auth login` flow (we delegate to git credential helper by design), `ssh-key`, `secret`/`variable` (org-level secrets differ structurally from anything we model)
- gh's extension/plugin marketplace: irrelevant for a single-purpose binary with a registry pattern
- Projects/boards: weak Forgejo parity, heavy surface
- `repo clone/create/fork/sync`: git already owns all of these; wrapping adds nothing observable
- Local-state features (gh has none either, mostly): everything stays request/response by design

## Deliberate divergences from gh worth keeping

1. Pull receipt instead of dumping payloads to stdout (gh always streams full output). Ours is receipt-on-pull, payload-only-through-view, which keeps the stdout contract per-command rather than per-flag-combination.
2. Unresolved-first defaults. gh has nothing analogous; it is our core differentiator for the working loop.
3. No interactive prompts anywhere (gh asks y/N in some flows): dry-run exits + `--yes` only, keeping pipelines safe.
4. gh shows tables on TTY too; we match it there — no divergence needed.

## Suggested slicing after 0.3.0

0.3.1: `review submit`, `comment add`, `close/reopen` (PR side), `diff` — four thin HTTP verbs that finish the loop
0.4.0 keeps its sync-engine scope; layer `api` passthrough + `search` in 0.4.x since they compliment webhook-era debugging
Tier 2 folds into minor releases by appetite; nothing there blocks anything
