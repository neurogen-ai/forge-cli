# Oracle counterpoint on the v0.3.0 plan

Deployed as devil's advocate against `plans/releases/v0.3.0.md`. Verbatim reply.

## Verdict

The plan is mostly sound and the build order is the right one, but one mechanism is load-bearing and wrong: the snapshot-promotion auto-mark. It tries to infer "the user pushed" from commit ancestry, which is not the same claim, and the ledger schema as written cannot support it correctly (the branch name is never recorded). I would shrink that mechanism to a warning, move auto-mark to explicit `seen` commands, keep JSON as the output default, and fix three schema gaps before stage 2. The rest of the plan is implementable as written.

## Decision 2, snapshot-promotion auto-mark

**The case against.** Three problems, in descending order of severity.

First, the schema cannot answer the promotion question. A snapshot is `{"sha": "a1b2c3d", "at": ..., "ids": [...]}` and promotion is "`merge-base --is-ancestor X origin/<branch>`" (plan section 3). But no branch is stored in the snapshot, and the check is "evaluated during normal forge invocations", which can happen on any checkout. Concretely: you fetch the conversation at HEAD X on `feat/sync`, switch to `master`, and run any forge command. Is the ancestor check against `origin/master`? Against the branch the PR points at (`PullRequest.Head.Ref` in `internal/api/types.go`)? The plan does not say. If it's against the PR's head ref, promotion requires the API to resolve the PR on every invocation just to know which ref to test. If it's against the current branch, promotion silently depends on what you happen to have checked out, which is not a defensible state machine for a file that survives restarts.

Second, the inference is wrong in both directions. Ancestry of X under `origin/<branch>` means "X exists on the remote branch". That is not "you pushed" and not "you reviewed". False positives: a teammate pushes the branch after you fetched, or you `git fetch` from a laptop while the push happened on your desktop and the state file on the laptop never promotes because `.forge/state.json` is per-machine by design. In both cases the promotion fires, marks items seen, and `pr new` shows nothing you ever read. False negatives: you rebase or force-push your branch. X is now orphaned, never an ancestor of anything, the snapshot never promotes, and `pr new` re-shows the same items forever, with the snapshot list growing one dead entry per rebase. The prune rule ("one entry per sha, oldest trimmed") does not remove entries that can never match.

Third, multi-PR-on-one-branch is mishandled. PRs #42 and #43 on the same branch get snapshots with the same sha under different PR keys. A single push promotes both PRs' item sets, so reading #42 marks items of #43 as seen. Items are identical by kind and id, so this may be tolerable, but the plan never states it, and it becomes an actual collision once per-item `unseen` overrides exist.

**What I would do instead.** Drop the ancestry inference from the promotion path. Keep the ancestry machinery exactly where it is correct: the per-item commit status block and `BranchSync` in plan section 4, which is a warning ("comment targets commits ahead of your checkout"), not a state transition. Auto-mark becomes: `forge pr new` promotes what it prints by default (`--no-mark` to keep them unseen), and `forge pr seen N` promotes the whole PR. That is explicit, testable, works across machines, and is exactly the "easy default path" the original requirement asked for. If push-triggered promotion stays, record `{"sha": X, "branch": "feat/sync", "pr": 42}` in every snapshot, promote only when the stored branch's remote ref contains X, and promote only into the stored PR's key. That fixes the schema gaps but not the teammate-push and rebase false cases.

## Decision 1, the `unseen_ids` negative set

**The case against.** A negative set that "overrides auto-mark until the next relevant event" needs a definition of "relevant event" and a garbage collection rule; the plan has neither. The interaction matrix is left open: if `pr unseen N` clears `seen_ids` but leaves `unseen_ids`, the PR's state becomes a set of items neither seen nor marked unseen whose display behaviour contradicts both sets. The two-set model has more states than the plan can reason about, and every one is a place where `pr new` output and the user's mental model silently disagree.

**What I would do instead.** Delete `unseen_ids`. One set, `seen_ids`, plus snapshots. "Unsee" is: remove ids from `seen_ids` and re-display them from `pr new`. The workflow the negative set was invented for disappears with the push-based auto-mark above, because marks now come from commands the user actually ran. Fewer states, no GC rules.

## Decision 3, `forge pr <N>`

**The case against.** Two costs, both real but small. Dispatch: `Run` resolves one token then joins at most one more to match registered names; a bare `forge pr 5` requires registering a command literally named `"pr"` whose `Run` interprets its first arg as a number, a special case in a registry where every other command is a fixed verb. Help: `forge pr --help` must show both the number-taking form and subcommands, and `forge pr --json` becomes positionally ambiguous with a PR number. The muscle-memory win buys less than it looks like because the valuable command in this release is `pr new`, which has no ambiguity at all.

**What I would do instead.** Keep `forge pr <N>` if wanted, but register `"pr"` explicitly, route `pr --help` to a combined page, require the first argument to parse as an integer or fail with exit 2 plus the usage list. Concede the rest: `pr new` with branch resolution is the right headline, and deprecating `pr conversation` with a notice is correct since `fetchConversation` is shared with the save path.

## Decision 5, table as the human default

**The case against.** The README states the contract: "writes JSON to stdout so scripts can parse it", and the PRD makes "stdout JSON is the stable, versioned shape" a core goal. Flipping the default to table inverts that: every script doing `forge pr list | jq` breaks, and machine output becomes opt-in via `--json`. That is a defensible product choice, but it is a breaking change to a stated contract and the plan should say so in one line, not bury it in a checkbox.

**What I would do instead.** Keep JSON on stdout as the default for data commands; add `--table` as the opt-in. Existing scripts, the bash-workflow replacement story, and agents consuming 0.2.x output keep working untouched. If table must be the default, pin a `FORGE_FORMAT` env, document the break, and freeze the column specs as versioned output like the JSON shapes.

## Decision 4, the central `internal/marker` package

**The case against.** The proposed API `Resolve(current branch) -> target` is PR-shaped. Issues have no branch; forcing them through means a no-op branch parameter, the classic sign the abstraction is one layer too high. Worse, v0.4.0's natural next source of seen state is server-side notification read flags, and the moment those disagree with the local ledger, semantics must be per-kind. A single marker package promising identical behaviour across kinds is the chokepoint that rewrite passes through.

**What I would do instead.** Concede the shared state layer: `internal/state` owning the ledger file, load/save/prune/version, is right and is where real duplication lives. Demote marker: keep a small state API (`AddSeen(key, ids)`, `Missing(key, ids)`, `Promote(key, ids)`) and let the pr and issue commands own their own resolution and promotion rules. Centralize file format and id-key logic where drift is dangerous; do not centralize semantics that will diverge.

## Decision 6, pagination fix scope

**The case against.** The plan asserts `GetReviews`/`GetReviewComments` truncate but this was not verified from code; `fetchConversation` calls them without page params, consistent with truncation but not proof of a server cap. If the server caps at 30 (Gitea/Forgejo default), `pr conversation` and `save pr-conversation` are silently incomplete today.

**What I would do instead.** Concede the fix, tighten scope: stage 1 adds a live-server verification task (PR with >30 reviews/comments, record the actual cap), apply the existing `List[T]` Link-header helper to both methods, fixture test with a synthetic `Link` header, document the cap in the README.

## Omissions

- **PR closure and branch deletion.** After merge or branch deletion, `origin/<branch>` no longer exists and snapshots never promote. Treat remote-ref-gone as terminal: prune the PR's snapshots with a stderr note, and decide whether closed-PR items auto-promote.
- **Squash-merge anchors.** Post-merge, every `commit_id` anchor becomes `unfetched` or `ahead`; document the expected post-merge status so nobody reads `ahead` after squash-merge as a bug.
- **Concurrent writes to `.forge/state.json`.** `store.Save` uses plain `os.WriteFile`, not atomic; two concurrent forge processes read-modify-write and lose updates. Specify temp-file-then-rename plus flock inside `internal/state`.
- **Offline behaviour.** State explicitly that `pr new` must not hard-fail on stale remote refs; label sync `unknown` and proceed from local objects.
- **Id key format is a blocker, not an open question.** The ledger schema already assumes prefixed keys (`"review-comment:981"`) while section 8 asks whether prefixes are needed. Verify whether comment and review-comment id spaces overlap before stage 2; if they overlap, unprefixed commands are a correctness bug.

## Changes I would insist on before implementation

1. Record `branch` and `pr` in every snapshot; move auto-mark onto `pr new` (with `--no-mark`) plus `pr seen N`. Keep ancestry checks only as warnings. If push-based promotion survives, it must use the stored branch and stored PR key and be documented best-effort.
2. Delete `unseen_ids`; specify atomic writes (temp+rename) under flock. Both are small changes removing the two most likely sources of silent state corruption.
3. Keep JSON as stdout default with `--table` opt-in, or document the default flip as a breaking change and version the column specs.
