# v0.3.0 proposal: unseen comments for the current branch

## Problem statement

The release note says "track diffs in the conversation somehow (maybe from the last push of that branch?)". That is a symptom, not a spec. The actual need has two parts.

First, coming back to your machine, one command with no arguments should show every conversation item you have not read on the PR belonging to your current branch, and warn you when a comment was written against commits your checkout does not contain. Today `forge pr conversation N` demands a number, returns everything every time, and throws away the commit fields the server already sends.

Second, whatever we ship should be the client half of the v0.4.0 auto-sync service. Not the service itself. We pick stable identifiers, a persisted state format, and a command whose output a daemon could later poll or produce. Nothing that forecloses that.

## Facts that constrain the design

1. **The server already sends the anchoring data.** Review comments carry `commit_id`, `original_commit_id`, `position`, `original_position`, `line`, `tree_path`, `diff_hunk`, and `resolved`. Reviews carry `commit_id` and a `stale` bool. `internal/api/types.go` drops all of these at decode time; only `DiffHunk` and `Path` survive onto `flatItem`.
2. **There is no server-side viewed state.** Forgejo exposes no read flag on comments. Seen tracking must live client-side. Notification unread flags and thread `resolved` answer different questions and are poor proxies.
3. **Force-push semantics.** After a force-push, `original_commit_id` is the only durable placement anchor; `commit_id` may be re-resolved or dangle. Every commit comparison must try `commit_id`, fall back to `original_commit_id`, and tolerate both failing.
4. **Issue comments have no commit association.** They can only be anchored by timestamp.
5. **"Is local behind" is a git question, not an API question.** `git ls-remote origin refs/heads/<branch>` (or `GET /repos/{o}/{r}/branches/{branch}`) yields the remote sha, `git rev-parse HEAD` yields local, and `git merge-base --is-ancestor local remote` decides exactly. The compare endpoint's ahead/behind fields are unverified, and walking paginated `commits[]` is slower and weaker than one merge-base call.
6. **State persistence is greenfield.** Save files are write-only snapshots; nothing in forge-cli reads back state. A cursor has no legacy constraints.
7. **Two things need verification before implementation:** exact field names on the review-comments endpoint against the live server, and pagination behavior (`GetReviews` and `GetReviewComments` currently do not paginate, so large PRs may truncate silently).

## Options

Ordered smallest to most ambitious. Options 2 and 3 assume option 1.

### Option 1: keep the anchors

Stop discarding commit data. Extend `api.ReviewComment` with `Position`, `OriginalPosition`, `CommitID`, `OriginalCommitID`, `Line`, `TreePath`, `Resolved`. Extend `api.Review` with `CommitID` and `Stale`. Pass them through `flatItem` and `groupedReview`.

```json
{
  "kind": "review-comment",
  "id": 981,
  "user": "alice",
  "body": "why not use context here",
  "path": "internal/api/client.go",
  "diff_hunk": "@@ -41,6 +41,9 @@",
  "position": 57,
  "original_position": 52,
  "commit_id": "a1b2c3d...",
  "original_commit_id": "9f8e7d6...",
  "resolved": false,
  "review_id": 310,
  "created_at": "2025-01-14T16:22:00Z"
}
```

No new commands, no state, no flags. Cost is plumbing plus fixture tests. Everything downstream needs these fields, so this ships first under any plan. It also forces the field-name verification question early, which is where the residual risk lives.

### Option 2: unseen as the default path

New command `forge pr unseen`, no positional argument. It:

1. Resolves branch to PR. `gitctx.CurrentBranch()`, then `ListPullRequests(state=open)` filtered on `head.ref == branch`. On no match: exit 3 with a hint to run `forge pr unseen N`. On multiple matches (possible after reopen): exit 2 listing candidates rather than guessing.
2. Loads the seen ledger from `.forge/state.json` in the repo root.
3. Fetches the conversation through the existing `fetchConversation` path.
4. An item is unseen if its `(kind, id)` is absent from `seen_ids` and its timestamp is newer than `last_viewed_at`. Ids are primary; the timestamp catches items whose ids were never recorded.
5. Prints unseen items plus a summary, then records them as seen. `--peek` prints without recording. `forge pr seen [--pr N]` marks everything current as seen without printing, for the "I read it via save files" case.

```json
{
  "pr": 42,
  "title": "Add sync stub",
  "branch": "feat/sync",
  "items": [
    {
      "kind": "review-comment",
      "id": 981,
      "user": "alice",
      "body": "why not use context here",
      "path": "internal/api/client.go",
      "created_at": "2025-01-14T16:22:00Z"
    }
  ],
  "counts": { "total_items": 31, "unseen": 2 }
}
```

Ledger at `.forge/state.json`, gitignored by convention:

```json
{
  "version": 1,
  "prs": {
    "git.ngenesis.co.uk/o/r#42": {
      "last_viewed_at": "2025-01-15T10:03:00Z",
      "seen_ids": [940, 951, 981]
    }
  }
}
```

Keyed by host, repo, and number so clones and repo renames behave. Prune `seen_ids` entries older than `last_viewed_at` on each write so it cannot grow forever. Degradation: detached or unborn branch exits 3 with a hint; offline fails through the normal exit-5 path. Server clock skew is why ids outrank timestamps.

What v0.4.0 inherits: the ledger format, the branch-to-PR resolver, and `pr seen` as its acknowledgment primitive.

### Option 3: commit awareness and the behind check

Layered on 2. Every item in conversation-shaped output gains a `commit` block, computed fresh each run and never persisted:

```json
{
  "commit": {
    "sha": "a1b2c3d...",
    "anchor": "commit_id",
    "status": "ahead"
  }
}
```

Status values and their meaning:

- `"local"`: the sha is an ancestor of HEAD. You have the code the comment discusses.
- `"ahead"`: the sha exists locally but is not an ancestor of HEAD. The comment targets commits your branch has moved past, or that sit on the remote side. This is the warning case from the maintainer's sketch.
- `"unfetched"`: the sha is absent from the local object database. You have not pulled.
- `"stale"`: `commit_id` dangled and `original_commit_id` was used, or both dangle after a force-push. Report which anchor survived.

Exact checks, in order:

1. `git cat-file -e <sha>^{commit}`. Failure means `"unfetched"`.
2. `git merge-base --is-ancestor <sha> HEAD`. Exit 0 means `"local"`, exit 1 means `"ahead"`.

One new gitctx helper, `BranchSync(root, branch)`, answers the behind question:

1. local sha from `git rev-parse HEAD`
2. remote sha from `git ls-remote origin refs/heads/<branch>`, falling back to `GET /repos/{o}/{r}/branches/{branch}` when origin is not the forge host or ls-remote fails
3. if the remote sha is unknown locally, either report divergence as unknown or run `git fetch origin <branch>` under `--fetch`
4. behind iff `git merge-base --is-ancestor local remote` exits 0

`forge pr unseen` surfaces the result in its summary:

```json
"sync": {
  "status": "behind",
  "local_sha": "b2c3d4e...",
  "remote_sha": "c3d4e5f..."
}
```

with `status` one of `synced`, `behind`, `ahead`, `diverged`, `unknown`. Offline, ls-remote failure degrades to `"unknown"` using a cached remote sha from the ledger if present; per-item commit statuses still compute from local git alone.

### Option 4: the conversation-state API

Mostly packaging of 1 through 3 rather than new machinery, but the packaging is what makes the v0.4.0 seam real:

- One shared type, `internal/conversation.Item`, produced by `fetchConversation`, carrying kind, stable id, timestamps, commit anchor, resolved state, and the computed commit and sync blocks. `pr conversation`, `save pr-conversation`, and `pr unseen` all render from it, so the shapes cannot drift.
- The ledger gets a documented version and a stated migration rule.
- A read-only `forge pr status` prints only the summary block (pr, counts, sync status) so scripts and the future daemon can poll cheaply without fetching conversations.

Where I would draw the line: no daemon, no webhook listener, no polling loop. Those belong to v0.4.0. What option 4 buys is a single `Item` contract and a versioned ledger that the service can consume unchanged.

## Recommendation

Ship options 1, 2, and 3 as three milestones inside v0.3.0. Their sum is option 4's core minus its extras.

- **M1, anchors.** Types, passthrough, fixtures pinned to verified field names. Lands immediately and retires the biggest uncertainty.
- **M2, default path.** `pr unseen`, `pr seen`, branch-to-PR resolution, `.forge/state.json`. This is the release headline.
- **M3, commit awareness.** Commit blocks, `BranchSync`, the `sync` block, `--fetch`.

Defer: `pr status` (cheap to add during M3 if wanted), pagination work beyond documenting current limits, anything daemon-shaped.

Why this slicing: M2 alone satisfies the letter of the request but produces silently wrong answers around force-pushes and unfetched commits, which is exactly the confusion the original note was circling. M3 is what makes the unseen list trustworthy, and it is cheap once M1 lands. The composition into v0.4.0 then falls out for free, because the sync service needs precisely what we now persist and compute: stable item ids, a seen ledger, and a local-versus-remote comparison routine.

## Open questions for the maintainer

1. **Auto-mark on view.** Having `pr unseen` record what it printed is convenient, but piping to jq technically counts as reading. Alternatives are requiring explicit `pr seen` (friction, weakens the default path) or auto-marking with a loud `--peek`. I favor auto-mark plus peek.
2. **Ledger sharing.** Should `.forge/state.json` ever be committed so seen-state travels between machines? I recommend gitignore and treat per-machine as correct.
3. **`--fetch` default.** On gives accurate statuses out of the box but performs network I/O and mutates git refs. I lean off by default with a visible warning when statuses come back `"unfetched"`.
4. **Field verification target.** Codeberg's swagger versus the self-hosted server may drift on `position`/`original_position` and the timeline endpoint. Which server is canonical for M1's fixtures?
5. **Pagination.** Fix the missing pagination on reviews and review comments during M1, or document the truncation risk and defer?
