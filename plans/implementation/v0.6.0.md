# Implementation plan, v0.6.0

## Context

**What exists:** after v0.5.0, main has the gh-spelled verb surface (`pr view/comment/review`), options-anywhere index parsing, `forge api` passthrough, anchored inline comments, `pr checkout`, and the tuicr `ForgeBackend` audit on record. The read/write verb machinery, TTY-aware table/JSON output, the exit-code contract 0–5, `Client.Do`/`DoRaw`, the `List` pagination helper, and the label-resolution and edit-verb patterns are all in place. Nothing on main fetches CI state, notifications, or repository search yet, and comments and labels have no mutation verbs beyond add.

**Areas touched:** `internal/api` (new transport methods and wire types, one probe-gated), `internal/cmds` (new command families plus one shared repeated-flag collector), `internal/gitctx` (one branch-head helper), `scripts`, `README.md`, repo-root `version.go`. No changes to `internal/cli`, `internal/table`, `internal/store`, or `internal/config`.

**Depends on:** `plans/releases/v0.6.0.md` is the binding authority for scope, the probe-first rule, and the parked list. `plans/implementation/archive/v0.5.0.md` supplies the baseline (gh spellings, `readDashInput`, anchor flags, registration seams). `plans/implementation/archive/v0.4.0.md` supplies the receipt conventions and `DoRaw`. `plans/releases/archive/v0.4.2.md` supplies the edit contract this release supersedes. `plans/proposals/archive/v0.3.0-unseen-comments.md` is the thread notifications picks up. The v0.5.0 release doc's contract audit (§6) explains why `search` and `sync-status` moved here. No `design/*` decisions exist.

**Preconditions:** v0.5.0's four PRs are merged on main; every branch cuts from that baseline. Merging to main is out of scope for every branch and PR; each PR ends reviewed and mergeable, and the release doc records where each PR ends.

**Descope homes (from the release doc, each with a named boundary):**

- Cross-repo `forge status` stays out (needs a repo-enumeration product decision; the search contract stays repo-scoped). Home: K forbids repo enumeration; L records the deferral.
- Review-comment editing stays out (ID spaces differ; `pr comment resolve` set the precedent). Home: C forbids review-comment targets; C's help page records the decision.
- No local seen ledger for notifications (v0.3.0's remote-resolved-state rule). Home: H forbids any local state file; `internal/store` stays untouched.
- `pr sync-status` stays one request and exit, no daemon, no polling loop. Home: J forbids retry, watch, or background flags; the v0.8.0 service builds on the one-shot shape.
- Assignee editing is not scheduled (rides the same edit verb on demand). Home: F forbids assignee flags.
- Auto-merge and webhook management stay parked. Home: every branch boundary.

## Goals

1. `forge pr checks N` shows commit statuses and, when the instance has Actions, Actions runs for the PR head ref; an instance without Actions gets a loud note line, not a failure.
2. `forge pr edit` gains reviewer request/removal and explicit field clearing, superseding the v0.4.2 title/body-only contract without breaking it.
3. Comments and labels become fully maintainable in the daily loop: comment edit/delete under both `pr` and `issue` spellings, and label create/edit/delete reusing the existing label machinery.
4. Conversation locking (`pr lock/unlock --reason`) works as an issue-backed mutation with the same receipt discipline as every other write verb.
5. `forge status` turns one repo into a dashboard of everything awaiting the caller: PRs assigned to them, review requests awaiting them, open issues. Repo-scoped, on the record.
6. Notifications surface server-side unread state (`forge notifications`, `forge notifications read ID...`) with no local ledger.
7. `forge search issues|prs` and `forge pr sync-status` land from the v0.5.0 re-scope with their specs unchanged: repo-scoped search over the existing pagination and table machinery, and a one-request in-sync/out-of-sync/no-pr answer for Starship to poll.
8. Version-dependent endpoints (Actions runs, issue locking, notifications) are probed against the live instance before their transports are committed.

## Success criteria

- The acceptance battery passes at every commit: `go vet ./...`, `gofmt -l .` prints nothing, `go build ./...`, `go test ./...`. No third-party dependencies.
- `forge version` prints `forge-cli v0.6.0`; every new `-h` page exits 0 and shows both spellings where an alias exists.
- `forge pr checks N` prints the head ref's commit statuses on any instance, and on an instance without Actions prints `note: Actions not available on this instance` and still exits 0 with the statuses.
- `forge pr edit N --add-reviewer U` and `--remove-reviewer U` both mutate the request list and print the updated pull request; the v0.4.2 title/body-only invocation keeps working byte-identically.
- `comment edit ID --body B` and `comment delete ID` work under both spellings, target issue comments only, and reject a review-comment ID with the standard error path. A missing body on edit exits 2 before any request.
- `forge pr lock N --reason R` and `forge pr unlock N` lock and unlock, with an instance that cannot lock surfacing the server message verbatim at exit 1.
- `forge status` prints all three sections from one invocation; it never queries a second repository.
- `forge notifications` lists unread first with a `--all` escape; `forge notifications read ID...` marks server-side read state; nothing writes to disk.
- `forge label create/edit/delete` reuse the label table machinery; a created label appears in the next `label list`.
- `forge search issues|prs QUERY [--state S]` sends `q`, `type`, and optional `state`, follows Link pagination, and renders the same table specs as `pr list`/`issue list` on a TTY.
- `forge pr sync-status [BRANCH]` makes exactly one API request, prints `in-sync`, `out-of-sync`, or `no-pr`, and exits 0 for all three; out-of-sync is data, not an error.
- `scripts/probe-v0.6.0.sh` exists with its findings recorded, and the Actions/lock/notifications transports cite the probe result, not a guess.

## Branch naming

Ordinary branches are `v0.6.0-<topic>`, PR heads are `v0.6.0-PR-<topic>`; topics are lowercase kebab-case and nothing else. Ordinary names validate against `^v\d+\.\d+\.\d+-(?!PR-)[a-z0-9-]+$`, PR heads against `^v\d+\.\d+\.\d+-PR-[a-z0-9-]+$`. A renamed branch is deleted and rebranched, never forked under a variant.

PR heads 2 through 4 each receive their own branches only; they already contain PR 1's commits through the direct B→… merges. That is the point of merging where the dependency exists, and each PR's diff against main turns clean the moment PR 1 lands. PR 5 is a single-branch PR; its head is `v0.6.0-release-close`, and a PR head with one branch gets no `PR-` branch of its own.

Shared seams:

- Registration seam. C, D, E, F, G, H, I, J, and K each append their own `Register` entries (or their family list in `internal/cmds`) and touch nothing else's; whoever lands second rebases. The seam is the existing `cli.Command`/longest-match dispatch contract.
- `internal/cmds/cmds.go` gains one function in F (`collectFlagValues`, generalized from `collectLabelNames` in `labels.go`; `collectLabelNames` delegates to it). B, C, D, E, G, H, I, J, and K add nothing to shared files; their commands live in new files, so the only rebase friction is registration order.
- `internal/api/types.go` is owned by B; every other branch extends its own api file (`checks.go`, `notifications.go`, `search.go`, or additions in `pulls.go`/`issues.go` matching the verb already there).
- Probe findings (A) feed E, G, and H. Each of those branches treats its probe finding as a design input: if the probe rejects the expected encoding, the wire types and the probe script's finding change together in that branch's first commit, and the contract skeleton below is amended in the same commit.

Position: first trunk; gates E, G, H, and therefore the release's riskiest surface. Touch boundary: repo-root `version.go`, new `scripts/probe-v0.6.0.sh`. 2. `chore(scripts): v0.6.0 endpoint probe`: follows the `probe-v0.5.0.sh` precedent. Against a live instance it checks Actions runs listing for a ref, `POST`/`DELETE` on issue lock (read-shaped probe only where a write would be visible; use a scratch issue), notifications list and mark-read, and PR reviewer request/removal. It prints which encodings the server accepted as labeled lines. Script-only commit, green by construction.

### Branch B, v0.6.0-api-types

Purpose: land the wire types that are not probe-gated, so the dependent branches differ only in their transport methods. 2. `feat(api): notification type`: `Notification` decodes list payloads, with the subject and repository slices the table needs. Read state stays server-side; nothing here fetches or stores more than the list and read endpoints return.
3. `feat(api): requested-reviewers field on pull request reads`: `PullRequest.RequestedReviewers` decodes onto the existing subset struct, feeding F's edit verb and K's review-request section. Fixture tests pin the decode.

### Branch C, v0.6.0-comment-mutations

## Foundational contracts

Review anchor: read these shapes, then check the code against them. Signatures and doc comments only.

```go
// internal/api/checks.go. Statuses decode here (not probe-gated); the
// ActionRun type and ListRunsForRef land in E1 with the probe-confirmed
// encoding. available=false means the instance has no Actions; the command
// turns that into the note line, so a missing capability is data, not an error.
type CommitStatus struct {
	State       string `json:"status"`        // pending|success|error|failure|warning
	Context     string `json:"context"`
	Description string `json:"description,omitempty"`
	TargetURL   string `json:"target_url,omitempty"`
}

func (c *Client) ListCommitStatuses(owner, repo, ref string) ([]CommitStatus, error)

func (c *Client) ListRunsForRef(owner, repo, ref string) (runs []ActionRun, available bool, err error)
```

```go
// internal/api/pulls.go. Reviewer request/removal are dedicated endpoints,
// not PATCH fields, so they are their own methods and return the updated
// pull request. RequestedReviewers on the read type feeds pr edit's
// --remove-reviewer defaults and forge status's review-request section.
func (c *Client) RequestReviewers(owner, repo string, index int, users []string) (*PullRequest, error)
func (c *Client) RemoveReviewers(owner, repo string, index int, users []string) (*PullRequest, error)
```

```go
// internal/api/notifications.go. Server-side read state only; nothing in
// this package touches disk. The write body's shape follows the probe
// finding; if the probe rejected the guess, the type, the transport, and
// the probe script's finding change together in H1.
type Notification struct {
	ID     int64  `json:"id"`

	Subject struct {
		Title string `json:"title"`

	} `json:"subject"`

}

func (c *Client) ListNotifications(all bool) ([]Notification, error)
func (c *Client) MarkNotificationsRead(ids []int64) error
```

```go
// internal/cmds/status.go. The dashboard is a registry of sections, fetched
// in registration order and rendered under their headings. A new section is
// one struct plus one registration entry; the dashboard loop never edits.
// Fetch receives the resolved current user so sections never re-resolve "me".
type statusSection interface {
	Title() string
	Fetch(ctx *cli.Ctx, me *api.User) ([]statusEntry, error)
}

type statusEntry struct {
	Kind   string // "pr" or "issue"; selects the render columns
	Index  int64
```

## Abstractions and what they absorb

- The status-section registry: `forge status` is a fixed loop over registered sections, so a new dashboard source (say, failed runs on my PRs) is one new section file, not an edit to the dashboard renderer. Absorbs: new dashboard sections, a changed "what needs my attention" definition.
- The search-kind registry: issues and prs differ by one query parameter and one row spec, both captured in the registry entry, so a third searchable kind is one entry. Absorbs: new search kinds, a row-spec change.
- The repeated-flag collector: `--add-reviewer`, `--remove-reviewer`, and `--label` all share one ordered collection path, so a new repeatable flag is a call, not a copy. Absorbs: any new repeatable value flag.
- The `available` flag on `ListRunsForRef`: capability absence is returned data rather than a special error path, so a second Actions-dependent command (v0.7.0's dispatch) inherits the same check. Absorbs: more Actions-gated commands, instance-version drift.
- `BranchHead` in gitctx: sync-status compares SHAs through one helper; v0.8.0's service reuses it instead of re-deriving git plumbing. Absorbs: any future local-branch/remote comparison.
- Alias-by-delegation (both comment spellings, both lock spellings): each spelling registers a thin struct delegating to one run, so receipts have exactly one implementation. Absorbs: new spellings, receipt-shape changes.
- The version constant bump as a release's first commit: the binary, tag, and release doc cannot disagree. Absorbs: every future release.
