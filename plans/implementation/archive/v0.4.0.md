# Implementation plan, v0.4.0

## Context

After v0.3.1, forge-cli has typed Forgejo API methods, the shared JSON client, the command registry, TTY-aware output selection, unresolved-first conversation views, explicit pull/cache writes, and PR batch creation. It can read and resolve conversation state, but it cannot submit a review, add a comment, change a PR's state, show a raw diff, or merge a PR.

This plan splits the current v0.4.0 release note at a clean boundary. v0.4.0 completes the request/response PR loop with write verbs and the diff view. Generic discovery is deferred to v0.5.0. The current one-line auto-sync service note moves to v0.6.0.

Files touched by the v0.4.0 implementation:

- `internal/api/client.go`, `internal/api/pulls.go`, `internal/api/issues.go`
- `internal/cmds/pr_review.go`, `internal/cmds/comments.go` (new), `internal/cmds/pr_state.go` (new), `internal/cmds/pr_diff.go` (new), `internal/cmds/pr_merge.go` (new)
- `internal/cmds/pr.go`, `internal/cmds/issues.go`
- `internal/store/store.go`
- API, command, and store tests beside those packages
- `README.md`, `plans/releases/v0.4.0.md`, `plans/releases/v0.5.0.md`, and `plans/releases/v0.6.0.md`

This plan depends on `plans/releases/v0.4.0.md` §§1-4, `plans/PRD.md` §§5-10, `plans/implementation/archive/v0.3.0.md`, `plans/implementation/archive/v0.3.1.md`, `plans/proposals/v0.3.0-extension.md`, and the neighboring release boundaries in `plans/releases/v0.4.1.md` and `plans/releases/v0.4.2.md`. The existing `README.md` is the documentation baseline. Do not change `plans/PRD.md`; later release plans extend its v0.1 non-goals.

Precondition: v0.3.1 is complete on the branch being used as the base. Merging any branch to `main` is out of scope.

## Release split

The current v0.4.0 note combines two kinds of work:

- v0.4.0: `pr review submit`, comment creation, PR close/reopen/ready, raw PR diffs, and PR merge.
- v0.5.0: `forge api`, `forge search issues|prs`, and the single-shot status check used by a Starship caller.
- v0.6.0: the existing auto-sync service idea from the one-line `plans/releases/v0.5.0.md` note.

The split keeps v0.4.0 on the existing typed API and command architecture. The passthrough command, search query model, and Starship-facing status command get their own plan after the raw response primitive from Branch C is available. See the v0.5.0 companion plan when that release is scheduled.

## Goals

1. Let maintainers complete the PR conversation loop without leaving forge-cli: submit a review, add issue-backed comments, close or reopen a PR, mark a draft PR ready, and merge a PR.
2. Keep all mutating commands single-shot and explicit. They send one request, print a small JSON receipt or updated resource, and never prompt, retry, or update branches automatically.
3. Add a pure `pr diff` view that preserves the server's text bytes and an explicit cache output path for agents that need a local copy.
4. Keep all Forgejo endpoint knowledge in `internal/api`; commands validate CLI spellings, map errors, and render output.
5. Preserve the v0.3.0 output and error contract. Existing commands and JSON shapes do not change.

## Success criteria

- `pr review submit` maps `approve`, `request-changes`, and `comment` to the exact Forgejo review events. Missing `--body` for `request-changes` exits 2 before any request.
- Both comment spellings send the same POST to `/repos/{owner}/{repo}/issues/{index}/comments` and print `{id, html_url}`.
- `pr close`, `pr reopen`, and `pr ready` use the exact PATCH bodies in the release note and print the updated PR JSON. A server that rejects `draft` exposes its message through the existing `APIError` mapping.
- `pr diff N` prints the response body byte-for-byte. `--patch` selects `.patch`; `--out` writes one overwriteable file below the configured PR savedir and prints a JSON receipt.
- `pr merge` requires exactly one strategy flag, sends Forgejo's `Do` body field, never deletes a branch after a failed merge, and reports a post-merge delete failure without hiding that the merge succeeded.
- `go test ./...`, `go vet ./...`, `go build ./...`, and `gofmt -l .` all pass. `gofmt -l .` prints nothing.
- The release documents no longer promise the deferred `api`, search, or auto-sync work under the wrong version.

## Tests

Each command test uses the existing `httptest` and `testCtx` fixtures in `internal/cmds`, and each API test asserts method, path, request bytes, decoded response, and non-2xx error type where applicable. Store tests use `t.TempDir()` and inspect the directory after each write. No unit test requires a live server, a token, `jq`, or a third-party Go package.

Receipt commands test JSON by unmarshalling into the named receipt type. The diff view has a byte-for-byte stdout assertion because adding a newline would corrupt a patch. Merge tests record request order so the no-delete-on-failed-merge rule cannot regress.

The final acceptance step runs the full local battery. Any manual live mutation must use a disposable PR and a token supplied through the environment; it is never part of CI and no credential is stored in the repository.

## Decision tree

```text
main at v0.3.1
├── A. review and comment writes     A1 → A2 → A3 ────────┐
├── B. PR state verbs                B1 → B2 ─────────────┤
├── C. raw diff and file output      C1 → C2 → C3 ────────┤
└── D. merge                         D1 → D2 ──────────────┘
                                                           ↓
                         E. release boundary, README, and acceptance
```

Branches A, B, C, and D can start in parallel from the v0.3.1 base. Within each branch, the numbered order is required. Branch C1 is also the future dependency for the v0.5.0 `forge api` command, but v0.4.0 does not add that command. Branch D needs only the existing `GetPullRequest` method when `--delete` is present.

A2, A3, B2, C3, and D2 all append registrations to `PRCommands()` or `IssueCommands()`. They are still parallel-safe because each branch owns its own command type, but the final integrator should resolve registration-order conflicts by keeping the registry list grouped by feature. No command may edit another branch's implementation to resolve a conflict.

Branch E waits for A-D. It is the only branch that edits release road-map files and the README. It must not absorb a late code fix; a failed acceptance check goes back to its source branch.

## Binding decisions

D1. The v0.4.0 boundary is the five loop-completing feature groups named in the first bullet of the release split. `api`, search, and the Starship status command are v0.5.0 work. The existing auto-sync service note becomes v0.6.0.

D2. `Client.DoRaw(method, path string, query url.Values, body []byte) (*RawResponse, error)` is the one raw transport entry point. `Do` and `DoRaw` share request construction, authentication, logging, status handling, and body reading through one private helper. No command builds an HTTP request itself.

D3. `store.WriteFile(dir, name string, data []byte) (string, error)` owns direct-child filename validation and overwrite behavior. `Write` and `WriteJSON` delegate to it. Diff output uses this method rather than adding a second file-writing path.

D4. `pr diff --out` is a boolean flag. It writes `<repo>-<N>.diff` for the default format and `<repo>-<N>.patch` with `--patch` below `[savedir] pr-conversation`. It does not accept an arbitrary output filename or introduce a new savedir key.

D5. Mutation output is fixed per command. Review submission prints `{id, state}`; comment creation prints `{id, html_url}`; state verbs print the updated PR object; diff `--out` prints `{path, bytes}`; merge prints `{index, action, head_deleted}`. These commands do not become table commands. Central format parsing still rejects `--table` for JSON-only commands, and `--json` does not change a receipt.

D6. When `pr merge --delete` is selected, the command fetches the PR before merging to capture `Head.Ref`. It attempts `DELETE /git/refs/heads/{ref}` only after a successful merge. If deletion fails, it prints the receipt with `head_deleted: false` and returns the mapped error with a merge-succeeded context. A failed merge never triggers a delete request.

D7. The merge request uses Forgejo's exact field names `Do`, `MergeTitleField`, and `MergeMessageField`. The strategy values are lower-case `merge`, `squash`, and `rebase`. No `DeleteBranchAfterMerge`, force-merge, or update-branch option is sent.

# Branch C, raw diff and file output

Branch C introduces the raw response seam needed by a text endpoint, then reuses the existing cache store for explicit diff output. The raw seam is intentionally usable by the deferred v0.5 `api` command, but that command is not registered here.

### Step C1: add the shared raw response transport

Refactor `internal/api/client.go` so JSON and raw calls share request construction. Add:

```go
// RawResponse is a successful response whose body the caller will interpret.
type RawResponse struct {
	Status      int
	ContentType string
	Body        []byte
}

// DoRaw sends one API request without JSON decoding its successful response.
// body is sent verbatim; nil means no request body.
func (c *Client) DoRaw(method, path string, query url.Values, body []byte) (*RawResponse, error)
```

Implement one private helper for the absolute URL, request body, `Authorization` header, timeout, verbose log line, response close, body read, and non-2xx conversion. `Do` must continue to JSON-marshal its `body`, set `Accept: application/json`, and decode its `out` exactly as it does now. `DoRaw` must set `Content-Type: application/json` when `body != nil`, omit `Accept` so text endpoints can use their normal representation, and return the response status, `Content-Type`, and bytes. Both methods return `*APIError` for non-2xx and an `IsNetwork` error for transport failures. Neither method exposes headers or retries.

Use `c.pageURL(path, query)` or an equivalent single URL builder so `Do` and `DoRaw` keep the same `/api/v1` path rules. Preserve the existing verbose log format and never log header values.

Extend `internal/api/client_test.go` with:

1. A text response test asserting status, content type, and exact bytes.
2. A raw request-body test asserting the body and content type.
3. A raw non-2xx test asserting `*APIError` and its status/message.
4. A raw transport failure test asserting `IsNetwork(err)`.
5. A regression assertion that the existing JSON `Do` path still decodes and sets its JSON headers.

Do not:

- add a second HTTP client or a streaming API;
- let callers bypass `/api/v1` or set the authorization header;
- make `Do` return raw bytes as a second result;
- change pagination's `getPage` behavior;
- implement the v0.5 `forge api` command in this branch.

Verify:


## Abstractions and future changes

- `SubmitReview` and `AddComment` keep endpoint knowledge in `internal/api`; a future Forgejo field addition changes the typed input or one method, not every command that calls it.
- `reviewEvent` keeps CLI-to-server event variation in one mapper; a future server event or a changed body rule edits one function and its tests.
- `commentAddCmd{kind}` keeps the shared issue-backed comment behavior in one command implementation; a future PR/issue comment option is added once rather than to two copied commands.
- `patchPull` centralizes PR PATCH request and decoding; future PR edit fields can reuse it without scattering method/path/error changes across state commands.
- `DoRaw` and its shared private transport helper keep non-JSON response handling in one place; the deferred `forge api` command and future text or binary endpoints can reuse it without new HTTP code.
- `store.WriteFile` separates filename choice from overwrite mechanics; release downloads or other non-JSON artifacts can add a filename at their caller without changing pull storage.
- `prDiffCmd` selects representation and storage policy while `GetPullDiff` owns the endpoint; a future diff format changes one selector and one API wrapper rather than a command-wide HTTP branch.
- `MergeInput` gives merge options a named wire type; a future Forgejo merge option can be added to that struct without changing flag parsing or request construction elsewhere.
- `MergeReceipt` records merge completion and branch cleanup separately; future post-mutation cleanup can add an explicit receipt field instead of hiding a partial result in a generic string.
- The v0.4/v0.5/v0.6 release boundary keeps discovery and long-running service concerns out of the write-verb PRs; future polling work can choose a service interface without changing one-shot command contracts.
