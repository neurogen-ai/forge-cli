# Implementation plan, v0.4.2

## Context

**What exists:** the current main branch contains the v0.3.1 CLI, typed Forgejo API methods, TTY-aware JSON/table output, pull and cache writes, issue label-name resolution, and the command registry. It already registers three-token commands such as `pr comment resolve`, but the dispatcher only tries one two-token join, so those commands are not reachable from the binary.

**Files touched:** `internal/cli/cli.go` and its tests; `internal/api/client.go`, `issues.go`, `pulls.go`, `types.go`, and new `releases.go` with API tests; new command files under `internal/cmds` plus `pr.go`, `issues.go`, `pull.go`, `pr_diff.go`, `cache.go`, and `views.go`; `internal/config/config.go`; `cmd/forge/main.go`; command, config, and store-path tests; `README.md`; and `plans/releases/v0.4.2.md`. The release reuses `store.WriteFile` from v0.4.0 and does not add a second filesystem writer.

**Depends on:** [`plans/releases/v0.4.2.md`](../releases/v0.4.2.md) for scope and release decisions, [`plans/PRD.md`](../PRD.md) sections 5 through 10 for precedence, output, errors, and exit codes, [`plans/implementation/v0.4.0.md`](v0.4.0.md) for `patchPull`, `DoRaw`, `RawResponse`, `store.WriteFile`, and `pr diff`, [`plans/implementation/v0.4.1.md`](v0.4.1.md) for the current release sequencing and acceptance style, and [`plans/implementation/archive/v0.3.1.md`](archive/v0.3.1.md) for registry, fixture, and list-rendering conventions.

**Precondition:** v0.4.0 and v0.4.1 are complete on the branch used as the base. The current checkout is still at v0.3.1, so finish those plans before starting this one. Do not duplicate `patchPull`, `DoRaw`, `RawResponse`, `store.WriteFile`, or the v0.4.0 diff implementation if they are already present. Merging any branch to `main` is out of scope.

## Goals

1. Add partial title/body edits for pull requests and issues, returning the updated resource as JSON.
2. List repository labels and add or remove existing labels from an issue or issue-backed pull request by name.
3. Make PR, issue, and repository web URLs easy to print or open explicitly in `$BROWSER`.
4. List releases, fetch one release by tag, and download selected or all release assets into the configured repository cache.
5. Keep endpoint knowledge in `internal/api`, file writes in `internal/store`, command variation in small parameterized commands, and all new output compatible with the existing CLI contracts.

## Success criteria

- `forge pr edit N` and `forge issue edit N` reject an invocation with no non-empty `--title` or `--body` before making an HTTP request. Valid calls send only the supplied fields to the correct PATCH endpoint and print the updated object.
- The binary resolves the longest registered command path, so both existing `pr comment resolve` and new `issue label add/remove` commands dispatch correctly. Two-token command behavior and family help remain unchanged.
- `label list` returns `[]api.Label` as JSON when piped and a fixed table on a TTY or with `--table`. Label mutations resolve names once, preserve input order, stop on the first failed removal, and emit a JSON receipt only after success.
- `pr browse N`, `issue browse N`, and `repo browse` print the server-provided `html_url`. `--open` launches the configured browser only when explicitly present, without shell evaluation or automatic opening.
- `release list` follows existing pagination and supports table defaults. `release get TAG` uses the tag endpoint. `release download TAG` writes exact asset names through `store.WriteFile`, overwrites the same filename on repeat runs, rejects an asset URL on a different host before sending the token, and emits a receipt with each written path and byte count.
- The seeded `releases` savedir is `.forge/cache/releases`, and `cache path` and `cache flush` include it automatically.
- `go vet ./...`, `test -z "$(gofmt -l .)"`, `go build ./...`, and `go test ./...` pass. No third-party dependency is added.

## Tests

API tests use the existing `httptest` client fixtures and assert methods, paths, request bodies, decoded results, headers, and `*APIError` values. Command tests use `testCtx`, `saveCtx`, and new handlers beside the existing command tests. The dispatch tests run `cli.Run` with fake commands, including a three-token name. Store-path tests continue to exercise the v0.4.0 `WriteFile` implementation rather than creating a command-side writer.

Every command with a new help page is covered by the existing `PRCommandsHaveHelpPages`, `IssueCommandsHaveHelpPages`, or a release-specific equivalent. Unit tests do not require a live Forgejo server, a token, a browser, or a shell. The final acceptance notes record that live asset redirects, live release payloads, and an actual browser launch are not part of the local test battery.

## Abstractions and future changes

- `lookupCommand` performs longest registered-prefix matching in one place. A future four-token command changes no dispatch code and does not need a special case.
- Typed `EditPullInput` and `EditIssueInput` values plus `patchPull` and `patchIssue` keep wire fields at the API boundary. A new editable field lands in its object-specific input and command parser, while state PATCH callers keep the same transport helper.
- `editCmd{kind}` shares validation, output, and help construction for PR and issue edits. A shared edit flag or error rule changes once, while divergent PR and issue fields remain separate in the API types.
- `collectLabelNames` and `resolveLabelIDs` are the only command-layer name-to-ID path. New label-name commands reuse the same exact-match and unknown-name behavior without copying the issue-create loop.
- `LabelReceipt` records the names the user requested rather than duplicating server label payloads. A future label action can add an explicit action-specific receipt without changing API methods.
- `browseCmd{kind}` owns the three resource lookups and `openInBrowser` owns process launching. A future browseable resource adds one lookup case and reuses the same safe browser behavior.
- `Release` and `ReleaseAsset` are the shared decoded server shapes. A new release view or asset selector reads the same fields instead of decoding ad hoc maps.
- `Client.Download` extends the raw transport helper from v0.4.0 to absolute, same-host URLs. A future binary endpoint can reuse authentication, timeout, logging, redirects, and API-error mapping without building an HTTP request in a command.
- `resolveConfiguredSavedir` centralizes config-key and repository-root resolution. A future cache-backed command uses the same seeded-key and relative-path rules instead of reproducing them.
- `ReleaseDownloadReceipt` contains per-file path and byte information. A later multi-file download can add a status field without hiding which files were written.

# Branch A, command dispatch

This branch fixes the registry boundary before any new three-token command is added. It is independent of the API and command feature branches.

### Step A1: resolve registered command paths of any length

Change `internal/cli/cli.go` by adding this private helper:

```go
// lookupCommand returns the longest registered command path beginning at
// argv[start]. If no path matches, it returns the first token, nil, and one
// consumed token so family-page and unknown-command handling keep their
// existing behavior.
func lookupCommand(reg *Registry, argv []string, start int) (path string, cmd Command, consumed int)
```

Try candidates from longest to shortest with `strings.Join(argv[start:start+n], " ")`. Return the first exact `Registry.Lookup` match. Replace the current one-join block in `Run` with this helper. Keep `wantsHelp` scanning only the tokens after the selected command path, keep `GroupPrefix` fallback based on the first token when no command matches, and leave global-flag parsing and `Prepare` ordering unchanged. A positional argument is not special to dispatch. It is simply part of a candidate that will fail to match, after which the registered command prefix is found.

Extend `internal/cli/cli_test.go` with these cases:

1. A registered `pr list` command still receives no command-path argument and still receives global flags after the path.
2. A registered `pr comment resolve` command receives `[]string{"88"}` from `Run([]string{"pr", "comment", "resolve", "88"}, ...)`.
3. When both `x do` and `x do extra` are registered, the three-token command wins for `x do extra value`.
4. `x do extra -h` prints the three-token command help, does not call `Prepare`, and does not run the command.
5. An unknown `pr something` still renders the existing PR family page or top-level usage as appropriate.

Do not:

- add command-specific dispatch cases for labels or comments;
- change `Registry.Register`, duplicate-name handling, `GroupPrefix`, or group-page rendering;
- consume command flags as global flags;
- change the `Command` interface or exit codes;
- merge this branch to `main`.

type browseCmd struct{ kind string } // "pr", "issue", or "repo"

func (c browseCmd) Name() string
func (c browseCmd) Summary() string
func (c browseCmd) RequiresAPI() bool
func (c browseCmd) HelpPage() string
func (c browseCmd) Run(args []string, ctx *cli.Ctx) error

func browseTarget(kind string, args []string, ctx *cli.Ctx) (url string, open bool, err error)
